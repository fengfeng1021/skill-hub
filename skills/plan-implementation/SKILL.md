# 建立實作藍圖

把「要做到什麼」轉成「按什麼順序改哪些位置、如何證明沒有改壞」。本 skill 只規劃，不設計產品需求，也不實作程式碼。

## 執行流程

1. 讀取需求契約、專案指示、現有架構、測試入口與受影響程式碼；不知道現況時先做唯讀探索，不憑空發明檔案。
2. 建立修改前基線：現有行為、公開介面、資料格式、事件、相依、驗證指令及已知失敗。使用者要求「保留、相容、不改」的項目必須留下可比較的基線證據。
3. 依 [實作藍圖方法與範本](references/implementation-plan-method.md) 把每個 `FR-###`／`NFR-###` 對應到一個或多個任務。
4. 先安排共用契約、資料與元件邊界，再安排功能、例外路徑、整合與收尾；依依賴排序，不用 UI 畫面順序假裝是實作順序。
5. 每個任務列出精確檔案或待建立路徑、責任、最小變更、測試／檢查、前置依賴與完成證據。不要寫「處理邏輯、改善 UX、補測試」這類無法直接執行的步驟。
6. 建立 `.agent/implementation-plan.md`；若專案已有計畫慣例，沿用既有位置並在工作流狀態記錄。
7. 做覆蓋與一致性自審，通過 Gate 後立即把計畫交給實作階段，不要求使用者再次點名下一個 skill。

## 規劃原則

- 一項任務只承擔一個可驗證責任；大型任務拆成能獨立失敗、修正與重驗的區塊。
- 指出修改現有檔案與新增檔案；不確定路徑時先探索，不可用猜測的路徑偽裝精確。
- 測試順序跟著風險：先建立會失敗的需求證據或基線，再實作，再跑最小相關驗證，最後跑整合 Gate。
- 保持現有架構與技術棧；若必須新增相依或改公開介面，列為明確決策與風險，不把它藏在任務細節。
- 對 API、支付、認證、資料遷移、分析事件或持久化格式，記錄修改前後可比對項目與回滾方式。
- 不得省略錯誤、空狀態、載入、恢復、無障礙、響應式、效能與安全中適用的需求。

## 計畫 Gate

- 契約中的每個 `FR`／`NFR` 至少被一項任務覆蓋，沒有孤兒需求或無來源任務。
- 每個任務都有檔案範圍、驗證方式、完成證據與依賴。
- 公開介面與「必須保留」行為已有修改前基線與比較方式。
- 任務順序能讓問題在最小範圍被發現；安全或相容性高風險不是留到最後才第一次檢查。
- 計畫沒有降低、改寫或超出需求契約；新發現的衝突已回到契約處理。

Gate 未通過就修計畫。計畫通過後，下游按 `T-###` 執行並把證據回寫；實作發現計畫錯誤時更新藍圖與變更紀錄，不得靜默偏離。
