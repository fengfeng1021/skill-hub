# 逐任務高品質 Coding Loop

一次只處理一個 `T-###`。目標不是把改動做大，而是讓每一步都能被證明、回退和審查。

## 1. Start：鎖定範圍

```text
workflowctl start-task T-001
```

只讀該任務的需求、相依任務、相關程式、測試和專案規範。先回答：

- 目前行為與缺口是什麼？
- 哪個最小觀察能證明問題存在？
- 哪些公開行為、資料或樣式必須保留？
- 修改責任應落在哪個既有邊界？

## 2. Characterize：先建立失敗證據

可行時先寫會失敗的自動測試；視覺或互動工作則建立可重複的瀏覽器步驟、截圖條件或可量測檢查。確認失敗原因正是缺少的需求，而不是測試本身壞掉。

若無法先建立失敗證據，記錄原因和替代驗證，不得直接省略。

## 3. Implement：最小完整修改

- 修改能完整滿足本任務的最小範圍，不順手重構無關區域。
- 沿用既有抽象；只有重複已出現或責任明確時才抽取新層。
- 在邊界驗證外部輸入；在正確層處理錯誤，不吞掉例外。
- 保持型別、命名、資料流和元件責任清楚，避免隱藏全域狀態與重複來源。
- 不留 TODO、假資料、除錯輸出、停用測試或只為通過測試的特殊分支。

## 4. Verify：先小後大

先執行最小相關測試，再依風險增加 typecheck、lint、build、整合和瀏覽器驗證。implementation Gate 固定要求 tests、typecheck、lint 與 diff-review；專案真的不適用時要保存 `not-applicable` 證據、原因和替代檢查，不能因 package script 缺失而靜默跳過。每次真實執行後記錄：

```text
workflowctl record-check T-001 --name unit --command "npm test -- feature" --exit-code 0 --evidence .agent/evidence/T-001-unit.txt
```

退出碼非零時，先判斷是實作缺陷、測試缺陷、既有基線失敗還是環境問題；不得把失敗刪掉或改成通過。

## 5. Review：審查本次 diff

逐項檢查：

- 每行是否服務本任務需求；是否有未解釋的範圍擴張。
- 邊界、資料流和公開介面是否仍一致。
- 是否複製邏輯、吞掉錯誤、引入 race、stale state 或資源洩漏。
- 錯誤、空白、載入、恢復、無障礙、響應式、效能與安全中適用者是否處理。
- 測試是否驗證外部可觀察行為，而不是鎖死實作細節。

必要時取得第二視角，但先重現審查意見再修改。

## 6. Complete：只有新證據才能完成

```text
workflowctl complete-task T-001 --summary "完成登入錯誤恢復與鍵盤焦點"
```

控制器應拒絕下列情況：沒有通過的最新檢查、證據檔不存在、需求沒有映射、任務受後續變更影響或仍有未記錄失敗。

任何後續修改影響本任務檔案時執行：

```text
workflowctl invalidate --files src/login.ts,src/login-form.tsx --reason "共用驗證流程已修改"
```

然後重新開始受影響任務。不得用舊測試結果支持新程式。
