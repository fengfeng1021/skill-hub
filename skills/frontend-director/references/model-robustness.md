# 較弱模型的執行護欄

本工作流不能改變模型權重，但可以減少模型需要同時記住、選擇和推理的內容。對工具調用或長任務穩定性較弱的模型，使用下列規則。

## 每次只提供一張工作卡

在每個行動前從狀態產生：

```text
Phase: implementation
Task: T-003
Requirements: FR-002, NFR-001
Read: 精確檔案與一份相關 reference
Change: 一個責任
Verify: 一個最小命令／步驟
Do not change: 明確邊界
Done when: 可觀察條件
```

不要要求模型同時比較所有階段、所有外部 Skills 和整份專案。

## 降低選擇負擔

- 優先沿用專案既有模式；只有既有模式無法滿足需求時才提出替代方案。
- 一次最多比較 2–3 個設計或架構方向，使用需求和證據選擇，不靠形容詞投票。
- 外部 Skill 只載入一個主能力和必要輔助；多個建議衝突時回到驗收契約。
- 把「探索、決策、實作、驗證」分開；不要讓同一次輸出同時發明需求和大量代碼。

## 防止假完成

- 工具沒有返回成功結果，就記為未驗證；不要從命令名稱推斷通過。
- 找不到檔案、Skill 或命令時先重新定位，不要用想像內容補齊。
- 每次壓縮、恢復或模型更換後先執行 `workflowctl status`，只相信工作區狀態與現有證據。
- 失敗最多在同一策略修正兩次；第三次先縮小重現、檢查假設或換驗證方法，避免 doom loop。

## 提升輸出品質

- 用真實內容、極端長度和錯誤資料驗證設計，不只生成理想範例。
- 先讓自動測試和控制器負責客觀條件，再把模型判斷留給視覺、產品取捨和可維護性。
- 重要里程碑取得獨立 review，但只傳原始需求、diff、畫面和測試結果，不傳預期答案。
