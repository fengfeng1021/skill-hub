# 檔案級實作規劃

把每個需求拆成能獨立失敗、修正和驗證的 `T-###`。先探索專案，再寫 `.agent/implementation-plan.md`；不得用猜測路徑偽裝精確。

## 探索順序

1. 讀專案指示、套件管理器、框架版本和原生命令。
2. 找到入口、路由、資料流、公開介面、元件邊界與測試位置。
3. 記錄使用者要求保留的行為、API、事件、資料格式和修改前證據。
4. 找出最小驗證指令與整合驗證方式；不存在的命令不要自行發明。

## 任務格式

```markdown
### T-001 — 一個可驗證責任
- Requirements: FR-001, NFR-002
- Depends on: none
- Read: src/..., tests/...
- Change: 精確描述最小修改
- Preserve: 公開行為／資料／相容性基線
- Failure first: 測試或重現步驟
- Verify: 最小相關命令與瀏覽器步驟
- Evidence: 預期證據路徑
- Rollback: 高風險時填寫
```

## 拆分規則

- 一項任務只負責一個可驗證結果；不要用「完成整個頁面」包住資料、UI、互動與測試。
- 先排契約、資料與共用邊界，再排功能和例外路徑，最後整合。
- UI 規劃先定設計方向和元件責任，不要在沒有方向時讓多個任務各自發明樣式。
- 新相依、公開介面修改、資料遷移、認證、支付和持久化格式必須成為明確決策與風險。
- 每個 `FR/NFR` 至少映射一個任務；每個任務也必須有來源需求。

## 控制器登錄

```text
workflowctl add-task T-001 --title "..." --requirements FR-001,NFR-002 --files src/a.ts,tests/a.test.ts --checks unit,typecheck
```

## Gate

- 需求覆蓋完整，沒有孤兒需求或無來源任務。
- 每個任務都有檔案範圍、失敗證據、驗證方式與完成證據。
- 任務順序使錯誤在最小範圍被發現。
- 計畫沒有降低或擴張驗收契約。
