## 原則

把規格視為「用自然語言寫成、也需要單元測試的程式」。需求品質與實作品質分開檢查：本階段先確認需求完整、清楚、一致、可量測且涵蓋重要情境，後續才驗證產品是否真的做到。

優先順序：

1. 使用者明確要求
2. 法規、安全、隱私與專案既有限制
3. 核心使用情境與成功條件
4. 可逆的產品預設
5. 實作偏好

## 契約範本

```markdown
# Acceptance Contract: <任務名稱>

## 目標

<一段話說明使用者要完成什麼，以及為什麼。>

## 範圍

### 包含
- <明確能力或交付物>

### 不包含
- <刻意排除，避免範圍漂移>

## 使用情境

### 主要情境
- Given <前置狀態>
- When <使用者行動>
- Then <可觀察結果>

### 替代／錯誤／空狀態／恢復
- <只保留適用的情境>

## 功能需求

- FR-001｜<單一、明確、可測試的結果>｜來源：使用者

## 非功能需求

- NFR-001｜<有門檻或明確驗證方式的限制>｜來源：專案／規範

## 假設與依賴

- A-001｜<合理預設>｜若錯誤會影響：<範圍／安全／UX／低>
- D-001｜<外部服務、資料、資產或環境>

## 風險

- R-001｜<風險>｜影響：高／中／低｜處理：<方式>

## 需求品質狀態

- 完整性：通過／待修
- 清晰度：通過／待修
- 一致性：通過／待修
- 可量測性：通過／待修
- 情境覆蓋：通過／待修

## 變更紀錄

| 時間 | 需求 ID | 舊值 | 新值 | 理由與授權來源 |
|---|---|---|---|---|
```

## 需求品質檢查

逐項問「規格有沒有寫清楚」，不要在這裡測實作：

- 完整性：主要流程、替代流程、錯誤、空狀態、載入、恢復與邊界是否有定義？
- 清晰度：模糊形容詞是否已量化或改成可觀察結果？
- 一致性：不同需求是否使用相同術語，是否彼此衝突？
- 可量測性：每項需求是否能由測試、檢查或人工觀察判定通過／失敗？
- 範圍：包含與排除是否明確，是否混入不必要功能？
- 非功能需求：效能、無障礙、相容性、隱私與安全是否按風險涵蓋？
- 依賴與假設：外部資料、服務、資產與合理預設是否留下紀錄？
- 追蹤性：每項需求是否有穩定 ID 與來源？

## 下游追蹤

實作計畫必須讓每個需求至少對應一項工作；最終驗證必須讓每個需求至少對應一份證據。測試不可依照已完成的錯誤實作降低條件。

```markdown
| 需求 ID | 計畫／實作 | 測試或檢查 | 實際證據 | 狀態 |
|---|---|---|---|---|
| FR-001 | `src/...` | `tests/...` | PASS／截圖／輸出 | 通過／失敗 |
```

## 方法來源

本方法以兩個 MIT 開源專案的公開流程為基礎重新整理，沒有複製其平台綁定指令：

- [GitHub Spec Kit](https://github.com/github/spec-kit)：規格驅動開發、可測試需求、成功條件、需求品質清單、需求／計畫／任務一致性與追蹤。
- [Superpowers](https://github.com/obra/superpowers)：先理解需求與範圍、規格自審、再建立可執行計畫；以規格覆蓋和證據防止 Agent 提前宣稱完成。
