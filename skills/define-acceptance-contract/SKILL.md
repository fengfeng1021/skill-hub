# 定義需求契約

在設計或寫程式前，先固定「什麼才算完成」。本 skill 只定義與檢查需求，不做 UI、架構或實作。

## 執行規則

1. 讀取使用者原始要求、附件與既有專案脈絡；原始要求的明確內容擁有最高優先權。
2. 擷取目標、使用者、主要情境、資料、限制、依賴、排除範圍與成功條件。
3. 對未指定細節採用合理且可逆的預設，記錄在「假設」；不要為一般細節打斷長任務。
4. 只有當選擇會實質改變範圍、安全／隱私或核心體驗，且沒有安全預設時，才一次提出最多 3 個問題。若使用者要求自主完成，選擇最保守合理的方案並記錄假設後繼續。
5. 依 [需求方法與範本](references/requirements-method.md) 建立 `.agent/acceptance-contract.md`。若專案已指定規格位置，沿用既有位置並在工作流狀態中記錄路徑。
6. 建立需求品質檢查表並最多自修 3 輪，直到沒有重大模糊、矛盾或不可驗證項目。
7. 把契約路徑與需求 ID 交給後續規劃、設計、實作、測試及安全階段；完成後立即繼續工作流，不要求使用者再次指定下一個 skill。

## 契約要求

- 以 `FR-###` 編號功能需求，以 `NFR-###` 編號效能、無障礙、安全、相容性等限制。
- 每項需求只描述一個可觀察結果，避免「快速、直覺、漂亮、完整、適當」等未量化詞。
- 為主要、替代、錯誤、空狀態、載入、恢復及邊界情境補上驗收條件；不適用時明確排除。
- 區分需求與實作：使用者指定的技術是限制；Agent 自選的技術放到後續計畫，不寫成產品需求。
- 保留來源追蹤：標示需求來自使用者、既有專案、外部規範或 Agent 假設。
- 不得因現有實作或測試比較容易通過而刪除、放寬或改寫需求。

## 變更控制

契約建立後視為工作流基準。後續若發現衝突：

1. 保留原需求 ID。
2. 在變更紀錄寫下舊值、新值、理由與授權來源。
3. 只有使用者新指示、客觀外部限制或經記錄的安全理由可以改變契約。
4. 實作困難、時間不足、測試已寫成另一種行為，都不是降低需求的理由。

## 交付給下游

後續階段只需讀契約，不必重新載入本 skill。最終品質閘門必須輸出：

| 需求 ID | 實作位置 | 驗證方式 | 證據 | 狀態 |
|---|---|---|---|---|

任何 `FR`／`NFR` 沒有實作或證據，都不得宣稱完整交付。
