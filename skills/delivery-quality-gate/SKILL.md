# 交付品質工作流

本 skill 有兩種模式：開發期間的持續品質 overlay，以及交付前的安全 finalizer。不要等全部寫完才開始驗證，也不要一開始載入所有品質與安全 skill。

## 啟動

1. 若存在 `.agent/acceptance-contract.md` 或專案指定的需求契約，先讀取並保留所有 `FR-###`／`NFR-###`。
2. 在既有工作流狀態中記錄品質證據；沒有上游工作流時建立 `.agent/quality-state.md`。證據放在 `.agent/evidence/` 或專案既有證據目錄。
3. 找出專案原生的測試、lint、typecheck、build 與安全指令，不猜測不存在的命令。
4. 建立「需求 ID → 驗證方式」對照。測試必須驗證契約，不得按照現有錯誤行為降低條件。

預設一份證據一個 Markdown 檔，ID／檔名用 `E-YYYYMMDD-HHMMSS-<scope>.md`。每筆至少包含需求／任務範圍、實際指令或人工步驟、時間、相關版本／commit、結果與 `valid` 狀態。任何影響同一範圍的程式變更都要把舊證據標為 `invalid` 並記錄原因。

## 模式 A：持續品質 Overlay

一次只處理一個可驗證任務。若上游有 `T-###`，依序完成「理解範圍 → 建立失敗證據 → 最小完整修改 → 最小相關測試 → diff 審查 → 最新證據」後才開始下一項；不要累積多個任務到最後一起驗證。若存在 `.agent/workflow-state.json`，以入口隨附的控制器記錄任務與檢查；不存在時才使用本 skill 的品質狀態。

每次有意義的程式碼修改後：

1. 跑受影響範圍的最小相關測試，保存指令、退出碼與關鍵輸出。
2. 檢查 diff 是否超出需求、破壞既有行為、複製邏輯、吞掉錯誤或留下暫時性程式碼。
3. 在階段 Gate 跑適用的 lint、typecheck、build、整合或瀏覽器驗證。
4. 程式變更後把舊證據標為失效；只有新執行結果能支持新的完成聲明。
5. 若 Agent 中存在 `verification-before-completion`，在需要宣稱通過的 Gate 載入它；不要只轉述本檔摘要。

在完整功能、跨模組重構或高風險里程碑後，若環境支援，載入 `requesting-code-review` 取得第二視角。收到意見時以 `receiving-code-review` 的方式先重現與驗證，再修正；不要因審查者措辭肯定就盲目接受，也不要因意見麻煩就跳過。

### 品質 Gate

- 每個任務都已獨立完成失敗證據、最小修改、驗證、diff 審查與最新證據閉環。
- 所有受影響需求都有測試或明確人工檢查。
- 最新驗證指令成功，且輸出與聲明一致。
- 新增錯誤路徑、邊界與恢復情境已有覆蓋。
- diff 中沒有未解釋的範圍擴張、秘密、除錯碼、無效註解或跳過測試。
- 審查發現已修正，或以證據記錄不採納原因與殘留風險。

Gate 失敗就回到實作修正並重新取得證據，不得向後推進。

## 模式 B：交付前安全 Finalizer

先依實際變更分級，再按需載入 Mantis；不要預先讀完全部安全 skill。

| 風險 | 典型變更 | 最低安全路徑 |
|---|---|---|
| 高 | 認證、授權、金流、個資、檔案上傳、外部命令或不可信輸入 | 從 `mantis-meta-agent` 路由，執行威脅建模、審查、重現與修補，修補後重跑品質 Gate |
| 中 | API、資料寫入、第三方整合、伺服器端渲染、持久化狀態 | 針對資料流、權限、注入、秘密與依賴做選擇性 Mantis 審查 |
| 低 | 純靜態內容、樣式或不接觸敏感資料的前端調整 | 檢查秘密、依賴、DOM XSS／注入面、外部資源與安全標頭影響 |

若安裝的安全入口名稱不同，使用 Agent 原生 skill 發現機制尋找 Mantis 或同等的 meta／threat-model／review 能力。低／中風險找不到時可執行同等最小檢查並明確記錄未使用的能力；高風險缺少威脅建模與深度審查能力時必須阻擋 production-ready，只能回報非正式交付或請使用者明確縮小範圍，不得用一般最小檢查代替。

安全發現必須包含嚴重度、可利用條件、影響範圍、證據與處置。修補會使既有品質證據失效，必須回到模式 A 重新驗證。

交付門檻：Critical／High 必須修正並重驗；Medium 必須有已驗證緩解措施，否則需要使用者明確接受風險；Low 可帶著影響說明交付。不要用「沒有時間」降低門檻。

## 需求追蹤與完成條件

最終輸出並保存：

| 需求 ID | 實作位置 | 驗證方式 | 最新證據 | 狀態 |
|---|---|---|---|---|

只有同時符合以下條件才可宣稱完成：

- 每個 `FR`／`NFR` 都有對應實作與最新證據。
- 適用的測試、lint、typecheck、build 與端到端檢查均已實際執行。
- 審查結果已處理；安全檢查已按風險完成。
- 未修正項目清楚記錄影響、理由與使用者需要知道的殘留風險。

最終回報列出實際執行的指令與結果、使用過的品質／安全 skill、需求覆蓋及殘留風險。沒有證據時只能說「尚未驗證」，不能說「應該通過」。
